# 教学微课 AI 开发平台：项目背景与建设分析

> 文档版本：V1.0  
> 编制日期：2026-08-02  
> 适用阶段：项目立项、需求评审、产品规划、MVP 范围确认  
> 技术约束：FastAPI、LangChain、LangGraph、SQLite、React/Vue，优先轻量化部署

---

## 1. 文档目的

本文档从教育业务、教师工作流、微课资源生产、生成式人工智能应用和平台建设约束五个层面，说明建设“教学微课 AI 开发平台”的现实背景、核心问题、目标用户、产品定位、建设边界和预期价值。

平台不是一个简单的“AI 文案生成器”，而是一个以课程目标为主线、以教师审核为最终决策、以多 Agent 协作为生产机制的完整教学资源生产系统。教师输入课程主题、授课对象、课时、课程任务、参考材料和个性化要求后，系统应生成彼此一致、可继续编辑、可导出的完整课程资源包，包括：

1. 教学设计；
2. PPT 课件；
3. 学习任务单；
4. 课后练习及参考答案；
5. 微课视频脚本；
6. 教师逐字稿；
7. 可选的课程摘要、知识点清单、评价量规和资源引用清单。

## 2. 政策与行业背景

### 2.1 教育数字化正在从“资源上网”转向“智能化生产与应用”

教育数字化早期建设重点是将课件、教案、视频和题库上传到平台；当前建设重点逐步转向：

- 课程、教材和教学全过程的数字化；
- 优质资源的体系化、结构化和动态更新；
- 人工智能辅助教师备课、教学、评价和教研；
- 资源从“统一供给”转向“按学段、学科、学情和任务生成”；
- 教师从资源消费者转向资源设计者、审核者和共建者。

教育部 2025 年有关部署明确提出推动课程、教材、教学体系智能化升级，将人工智能技术融入教育教学全要素、全过程，并强调教师数字教学能力、优质资源建设、内容质量和安全治理。

因此，本项目的机会不只是提高文档生成速度，而是将“课程设计逻辑、资源生产流程、质量评价流程”沉淀为一个可复用的智能工作台。

### 2.2 真实精品课和微课交付通常是“资源包”，而不是单个视频

教育场景中的微课交付往往要求同时包含：

- 微课视频；
- 教学设计；
- 学习任务单或导学案；
- 课件；
- 作业练习；
- 必要的实验、案例或拓展资源。

这意味着平台必须首先建立一个统一的课程蓝图，再让各资源生成 Agent 基于同一蓝图工作。若各模块各自独立调用模型，容易出现以下问题：

- PPT 与教学设计目标不一致；
- 任务单包含未讲授知识；
- 练习题难度超出授课对象；
- 视频脚本时长与课程时长不匹配；
- 教师逐字稿与 PPT 页序不同；
- 同一概念在不同文档中术语不统一；
- 参考材料中的事实被模型随意改写。

平台必须解决“多资源一致性”，而不仅是“多资源都能生成”。

### 2.3 教师使用生成式 AI 的核心诉求是“减负不失控”

教师希望 AI 帮助完成重复、耗时和格式化工作，但通常不愿完全放弃对以下内容的控制：

- 教学目标；
- 内容取舍；
- 价值导向；
- 学情判断；
- 重点难点；
- 教学活动；
- 评价标准；
- 最终表述；
- 是否引用教材或校本材料。

因此，平台应遵循“AI 生成、教师决策、过程可回溯”的原则。生成结果应支持查看依据、局部重写、版本比较、人工审批和导出，而不是把教师限制在一次性生成结果中。

### 2.4 生成式 AI 进入教育必须同时处理质量、安全与伦理

教育内容比普通营销文案对准确性、适龄性、价值导向和可解释性要求更高。平台至少需要处理：

- 事实错误和知识幻觉；
- 学科术语错误；
- 年级或专业难度不匹配；
- 教材内容引用失真；
- 个人信息和学生数据泄露；
- 上传材料版权与授权问题；
- 不恰当、歧视性或有害内容；
- 教师过度依赖 AI；
- 生成内容来源不可追踪；
- 模型供应商和数据跨境风险。

因此，质量审核 Agent 和人工审核节点是系统核心组件，不是后期附加功能。

## 3. 真实微课开发流程分析

### 3.1 传统流程

一个较完整的微课开发过程通常包括：

1. 明确课程标准、人才培养方案或教学大纲；
2. 确定授课对象和先备知识；
3. 划定一个适合微课的知识单元；
4. 设置可观察、可评价的教学目标；
5. 分析重点、难点和易错点；
6. 设计课程结构和时间分配；
7. 设计导入、讲解、示例、互动、总结和评价；
8. 编写教学设计；
9. 设计 PPT；
10. 编写学习任务单；
11. 设计练习题和答案；
12. 编写视频分镜与旁白；
13. 编写教师逐字稿；
14. 多轮核对各资源的一致性；
15. 试讲、计时和修改；
16. 输出、归档和共享。

教师最耗时的环节通常不是写出某一段文字，而是反复在各资源间同步修改。例如教学目标变化后，需要同时调整 PPT、任务单、练习和逐字稿。

### 3.2 AI 平台应重构的流程

平台将传统“文档串行制作”重构为**“项目式服务 + 课程大纲驱动 + 模块化 Agent 对话协作”**的并行生产流程：

```mermaid
flowchart TD
    A[教师创建课程项目并输入提示词与材料] --> B[总控 Agent：需求解析与大纲蓝图生成]
    B --> C{教师确认课程大纲}
    C -->|对话微调| B
    C -->|锁定确认| D[总控 Agent 初始化各资源模块与专属 Agent 上下文]
    D --> E[项目主视图：模块 Tab + 专属 Agent 对话框 + 右侧文件预览]
    E --> E1[大纲/蓝图模块 (总控 Agent)]
    E --> E2[教学设计模块 (教学设计 Agent)]
    E --> E3[PPT 课件模块 (PPT 课件 Agent)]
    E --> E4[学习任务单模块 (任务单 Agent)]
    E --> E5[课后练习模块 (练习题 Agent)]
    E --> E6[视频脚本模块 (视频脚本 Agent)]
    E --> E7[教师逐字稿模块 (逐字稿 Agent)]
    E1 & E2 & E3 & E4 & E5 & E6 & E7 --> F[教师在各模块 Tab 内与专属 Agent 协同对话与局部修订]
    F --> G[系统规则检查与质量审核]
    G --> H[终审与一键导出完整课程包]
```

关键变化是：

- **项目制管理**：所有资源围绕统一的“课程项目”组织，左侧侧边栏随时切换项目；
- **总控 Agent 初始化**：教师提供初始 Prompt 与要求后，总 Agent 负责解析需求并生成课程大纲，确认后自动**初始化**各个子 Agent 的专属 Context 和基础生成任务；
- **模块化专属对话**：切换顶部 Tab 进入具体模块（如 PPT 课件），中间为该模块 Agent 的专属对话/交互窗口，教师可针对该模块发送指令；
- **右侧实时文件预览**：界面右侧实时呈现该模块当前最新生成的文件产物、状态与历史版本；
- **所有资源共享统一大纲**：子 Agent 基于总 Agent 初始化的课程大纲进行协作，确保多资源逻辑一致。

## 4. 目标用户与典型场景

### 4.1 核心用户

#### 4.1.1 中小学教师

主要需求：

- 对齐课程标准和教材；
- 符合学段认知特点；
- 生成预习、课堂和课后任务；
- 控制作业量和难度；
- 适配线上、线下或混合教学；
- 生成适龄表达和情境案例。

#### 4.1.2 高校教师

主要需求：

- 对齐人才培养目标和课程大纲；
- 处理概念、公式、案例、实验和前沿内容；
- 生成知识目标、能力目标和素养目标；
- 支持翻转课堂、案例教学、项目式学习；
- 生成课程思政融合点但避免生硬拼接；
- 支持中英文课程资源。

#### 4.1.3 职业院校教师和企业培训师

主要需求：

- 以岗位任务、工作过程和技能标准组织课程；
- 生成实训任务、操作步骤和评价量规；
- 突出安全规范和质量要求；
- 支持情境化、项目化和任务驱动教学；
- 形成可执行的学习工作页。

#### 4.1.4 教研员、课程负责人和教学管理者

主要需求：

- 统一资源模板和质量标准；
- 建立校本资源库；
- 审核教师生成内容；
- 查看课程生产进度；
- 统计资源使用和修改情况；
- 沉淀优秀模板和评价规则。

### 4.2 典型使用场景

#### 场景 A：从零生成一节微课

教师仅输入主题、对象、时长和目标，系统通过追问补充信息，生成完整课程包。

#### 场景 B：依据教材或大纲生成

教师上传教材章节、课程标准或教学大纲，系统提取知识点、术语和要求，基于材料生成资源，并标注引用依据。

#### 场景 C：改造已有课件

教师上传旧 PPT、教案或讲稿，系统识别结构和问题，生成优化版资源，而不是完全推倒重来。

#### 场景 D：只重做一个资源

教师保留已确认的课程蓝图，只重新生成某几页 PPT、某道题或某一段逐字稿。

#### 场景 E：按不同学情生成多个版本

同一知识点生成基础版、标准版和提高版，或针对不同专业生成不同案例。

#### 场景 F：参赛或精品课资源制作

按照指定模板和检查清单生成完整材料，并进行格式、时长、资源完整性和一致性检查。

## 5. 当前痛点及系统应对策略

| 真实痛点 | 造成的后果 | 平台策略 |
|---|---|---|
| 输入信息不完整 | 生成内容空泛 | 需求解析 Agent 自动识别缺失项，允许智能补全或教师确认 |
| 教学目标不可评价 | 活动和练习无法对齐 | 目标设计 Agent 将目标转换为可观察行为和达成指标 |
| 多份资源互相矛盾 | 教师二次修改成本高 | 统一 Course Blueprint，所有 Agent 只读同一权威状态 |
| 生成结果“像文章不像课” | 缺少教学过程 | 强制输出导入、活动、提问、反馈、评价和时间分配 |
| PPT 文字过多 | 无法直接授课 | PPT Agent 使用页级信息密度、版式和演示规则 |
| 练习题质量不稳定 | 超纲、重复、答案错误 | 题目 Agent + 独立校验 Agent + 目标覆盖矩阵 |
| 逐字稿时长失控 | 录制时超时 | 按语速估算字数，脚本与 PPT 页序和时间轴绑定 |
| 模型幻觉 | 教学错误 | 参考材料优先、来源记录、事实检查和不确定性提示 |
| 一次生成不可控 | 教师不信任 | 关键节点确认、局部重写、版本比较、撤销恢复 |
| 格式导出差 | 不能直接使用 | 模板化 DOCX/PPTX/Markdown/PDF 导出 |
| 生成成本不可控 | 平台运营困难 | 模型分级路由、缓存、并行任务和局部重生成 |
| 数据安全不明确 | 学校不敢使用 | 本地 SQLite、可配置模型、脱敏、权限与审计 |

## 6. 产品定位

### 6.1 一句话定位

> 一个由教师主导、以课程蓝图为中心、通过多 Agent 协作生成并校验完整微课资源包的轻量化教学内容生产平台。

### 6.2 产品不是

- 不是单纯的聊天机器人；
- 不是只生成 PPT 的工具；
- 不是自动替代教师决策的“无人备课系统”；
- 不是第一阶段就承担视频渲染和数字人合成的重型平台；
- 不是通用网盘或完整 LMS；
- 不是考试管理系统。

### 6.3 第一阶段产品边界

MVP 聚焦“备课与资源生产”，不做：

- 学生端完整学习平台；
- 直播教学；
- 复杂班级管理；
- 在线考试监考；
- 数字人视频自动合成；
- 大规模分布式训练；
- 多租户计费系统；
- 复杂工作流自由编排器。

这样可以在 FastAPI + LangGraph + SQLite + Vue/React 的单体架构中快速完成可用产品。

## 7. 建设目标

### 7.1 业务目标

1. 将完整微课资源初稿生产时间从数小时降低到分钟级；
2. 降低教师在格式整理、内容同步和重复改写上的时间；
3. 提高教学目标、活动、练习和讲稿的一致性；
4. 让教师可以基于学校模板快速形成标准化资源；
5. 形成可复用的课程蓝图、提示模板和质量量规；
6. 支持校本知识材料和优秀案例的持续沉淀。

### 7.2 产品目标

- 输入门槛低：表单和自然语言均可；
- 生成过程透明：显示 Agent 进度、问题和返工；
- 结果可编辑：支持局部修改，不强迫全量重生成；
- 资源可导出：PPTX、DOCX、Markdown、JSON，后续可选 PDF；
- 内容可追踪：保存输入、版本、来源和审核记录；
- 模型可替换：支持 OpenAI、DeepSeek、通义千问等兼容接口；
- 部署轻量：单机可运行，后期可平滑迁移至 PostgreSQL 和任务队列。

### 7.3 质量目标

每个课程包至少通过以下检查：

1. 目标与活动对齐；
2. 目标与练习对齐；
3. 知识点覆盖完整；
4. 内容不超出输入材料或明确标注拓展；
5. PPT、脚本和逐字稿顺序一致；
6. 总时长在允许误差内；
7. 语言适合授课对象；
8. 答案正确且可解释；
9. 不含明显敏感、违法或不当内容；
10. 资源字段完整、文件可打开。

## 8. 多 Agent 建设必要性

单 Agent 可以生成一份较长文本，但难以同时兼顾教育学、学科内容、PPT 设计、题目设计、脚本节奏和一致性审核。多 Agent 的价值并不是模拟多个“人格”，而是进行职责隔离和可控编排。

### 8.1 职责隔离

- **Master Agent (总控 Agent)**：专注需求解析、大纲蓝图生成与子 Agent 会话初始化；
- **教学设计 Agent**：专注教学目标可评价性与活动设计对话；
- **PPT 课件 Agent**：专注演示卡片排版结构与视觉提炼对话；
- **学习任务单 / 练习题 Agent**：专注分层题目、答案解析与梯度设计对话；
- **视频脚本 / 逐字稿 Agent**：专注时间轴节奏、分镜提示与口语化讲述对话；
- **QA & Export Agent**：独立审查多模块一致性问题并打包导出文件。

### 8.2 降低上下文混乱

每个 Agent 保持独占的模块 Chat 会话与受限上下文，只接收并更新当前模块的 Artifact 状态，避免将全局所有资源的复杂要求混合放入单一 Prompt 中。

### 8.3 支持局部重生成

教师修改“教学对象”后，系统可以判断哪些资源受影响，而不是无条件重做全部内容。

### 8.4 支持模型分级

高推理模型用于课程蓝图和质量审核，低成本模型用于格式转换、摘要和局部润色，以降低成本。

## 9. 核心设计原则

### 9.1 教师最终负责

AI 结果默认是“建议稿”，发布和导出前应由教师确认。

### 9.2 课程蓝图是唯一事实源

课程目标、知识点、重点难点、时间结构、术语和资源编号统一存储，不允许各 Agent 私自定义另一套结构。

### 9.3 先结构后内容

先确定课程蓝图和资源大纲，再生成长文本和文件，降低返工成本。

### 9.4 生成与校验分离

不能让生成 Agent 自己作为唯一审核者。至少使用规则校验和独立 QA Agent 两层检查。

### 9.5 默认可编辑而非默认完美

产品应优化“生成—修改—重生成—对比—确认”闭环，而不是宣传一次生成即可直接发布。

### 9.6 轻量起步、保留迁移能力

- MVP：SQLite、单机文件存储、进程内异步任务；
- 成长阶段：PostgreSQL、Redis、对象存储、独立 Worker；
- 不在 MVP 过早引入 Kubernetes、复杂微服务和向量数据库集群。

### 9.7 内容安全和数据安全前置

敏感词、个人信息、上传材料、模型调用日志和导出权限在设计阶段就纳入。

## 10. 成功指标

### 10.1 使用效率指标

- 创建课程需求平均用时；
- 首次生成完成时间；
- 单资源重生成时间；
- 教师从初稿到确认的修改轮次；
- 导出成功率。

### 10.2 内容质量指标

- 课程目标覆盖率；
- 练习与目标对齐率；
- 多资源术语一致率；
- 时长误差；
- 教师评分；
- QA 首次通过率；
- 事实性问题数量。

### 10.3 产品使用指标

- 周活跃教师数；
- 新建课程项目数；
- 课程包导出数；
- 模板复用率；
- 局部编辑和重生成使用率；
- 课程项目完成率。

### 10.4 技术指标

- API 可用性；
- Agent 节点失败率；
- 可恢复任务比例；
- 模型调用平均延迟；
- Token 和模型成本；
- 文件生成失败率；
- 数据备份恢复成功率。

## 11. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 教学内容错误 | 直接影响授课质量 | 材料优先、知识审核、答案校验、教师终审 |
| Agent 数量过多 | 成本高、流程慢 | MVP 控制在 8—10 个核心节点，部分能力用普通函数完成 |
| 所有内容并行导致不一致 | 返工复杂 | 蓝图确认后并行；统一引用资源 ID |
| SQLite 写并发有限 | 高并发时阻塞 | MVP 单机串行写；后续迁移 PostgreSQL |
| 长任务被进程重启中断 | 用户体验差 | LangGraph checkpoint、任务状态持久化、幂等节点 |
| PPT 生成效果普通 | 用户不满意 | 模板驱动、限定版式、允许上传模板、PPT 内容与渲染分层 |
| 文件解析质量不稳定 | RAG 依据不可靠 | 支持人工校正文档摘要和知识点；保存解析状态 |
| 成本不可预测 | 难以运营 | 预算上限、模型路由、缓存、局部生成、Token 统计 |
| 用户上传敏感信息 | 合规风险 | 告知、脱敏、最小化存储、可删除、访问控制 |
| 教师直接发布未审核内容 | 质量风险 | 导出前提示、审核状态、可选强制审批 |

## 12. 建议的 MVP 验证假设

MVP 不需要证明平台可以自动完成所有教育工作，而应验证以下假设：

1. 教师愿意通过结构化表单输入课程需求；
2. “先生成课程蓝图再生成资源”比直接生成多个文档更可信；
3. 教师最重视教学设计、PPT、任务单、练习、视频脚本和逐字稿的一致性；
4. 局部修改和局部重生成比整包重做更有价值；
5. 教师愿意审核 AI 生成内容，但希望系统先指出风险；
6. 可编辑 PPTX/DOCX 比单纯展示文本更能促成实际使用；
7. 单机轻量部署足以支撑早期试点。

## 14. 结论

该平台的真正价值是把教师隐性的备课经验转化为可执行、可审核、可复用的智能工作流。轻量化技术栈足以完成第一阶段，但产品设计必须从一开始就具备三项能力：

1. **统一课程蓝图，确保多资源一致；**
2. **多 Agent 分工与定向返工，确保生成可控；**
3. **教师审核、版本和来源追踪，确保教育内容可信。**

只有同时满足这三项要求，平台才会从“看起来很强的 AI 演示”转变为教师愿意持续使用的真实教学生产工具。
